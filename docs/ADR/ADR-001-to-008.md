# ADRs (status: **Proposto**, aguardam aprovação)

## ADR-001 — Multi-tenancy por coluna `organization_id` + RLS (banco único)
Contexto: custo mínimo e operação simples. Decisão: schema único, `organization_id NOT NULL` em tabelas privadas, FKs compostas `(organization_id, id)`, RLS em todas. Alternativas: schema por tenant (migrações caras no free tier), projeto por tenant (custo). Consequência: isolamento depende de RLS correta, então testes de isolamento são bloqueantes (P0).

## ADR-002 — Hospedagem: Cloudflare Workers com Static Assets (frontend + API no mesmo Worker)
Mesmo domínio elimina CORS e simplifica cookies/CSRF. Alternativa: Pages + Worker separado. A confirmar na Fase 1A conforme estado atual da documentação Cloudflare (Pages vs Workers Static Assets). Reversível.

## ADR-003 — Worker repassa o JWT do usuário ao Supabase; `service_role` excepcional
Preserva RLS. `service_role` só para outbox, webhooks e provisionamento, com escopo mínimo e auditoria. Alto impacto de segurança, exige aprovação.

## ADR-004 — Autorização: RBAC granular + escopo de unidade + vínculo clínico
Permissões globais (`permissions`), papéis por organização (`roles`), atribuições com escopo opcional de unidade (`user_role_assignments`). Acesso clínico exige adicionalmente vínculo profissional-paciente/atendimento e finalidade registrada. Funções SQL `SECURITY DEFINER` mínimas e revisadas para uso em RLS.

## ADR-005 — Núcleo único de agenda com `EXCLUDE USING gist` em `tstzrange`
`resource_allocations(resource_type, resource_id, period tstzrange)` com `EXCLUDE ... WHERE (status = 'active')`, intervalo `[)`, extensão `btree_gist`. Reserva multi-recurso em uma transação (todas as alocações ou nenhuma). Nível de isolamento READ COMMITTED + constraint (a constraint garante a exclusão); SERIALIZABLE não é imposto.

## ADR-006 — Rate limiting: tabela Postgres (início) com opção de Cloudflare KV/Durable Objects
KV é eventualmente consistente (contadores imprecisos). Para limites estritos (login, OTP) usar Postgres (janela fixa, `INSERT ... ON CONFLICT`) ou Durable Objects (decisão futura por custo). Limitação documentada.

## ADR-007 — Idempotência por `idempotency_keys(scope, key)` único + TTL
Cabeçalho `Idempotency-Key` obrigatório em agendar/remarcar/cancelar/pagar/estornar/enviar mensagem. Armazena hash da requisição, status e resposta; mesma chave com payload diferente retorna 422.

## ADR-008 — Antimalware de uploads: quarentena + pipeline assíncrono
Arquivo vai a bucket `quarantine`, status `pending`, só é liberado após varredura. Mecanismo (ex.: ClamAV em serviço externo, ou API de varredura) **não definido e pode gerar custo**: até aprovação, uploads de documentos clínicos permanecem **desabilitados** e a UI não afirma proteção antimalware.

## ADR-009 — Imutabilidade: registros clínicos finalizados, auditoria e livro financeiro
Triggers que bloqueiam UPDATE/DELETE em registros `finalized`, `audit_logs`, `data_access_logs` e `financial_transactions` confirmadas; correções por adendo/estorno. `REVOKE UPDATE, DELETE` para os papéis da aplicação.
